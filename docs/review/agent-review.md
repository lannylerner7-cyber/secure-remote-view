# Agent review — audit #10

## Boundary and method

Read-only static review of all 58 non-bin/obj files under `imports/connectlive/agent`, including the test source, packaging references, assets and documentation. Read the 17 agent route modules, authentication/authorization helpers, recorded-authorization migration, release schema and signal-deduplication index. Also read the desktop packaging script/signing helper and the Agent ZIP's directory, README and launcher **without extracting or executing its executable**.

No builds, tests, live HTTP requests, workflow operations or Windows execution were performed. Archive CRC/hash/PE/signature/source-to-binary integrity checks belong to the main reviewer; this document does not claim their results. Existing documentation's test/health claims were read, not independently reproduced. No credentials/configuration values are reproduced.

`agent-coverage.json` is a file-level inventory: `reviewed` means the stated static examination, **not** approval or runtime verification. Documentation was checked for contract drift; SVG read as branding; ICO identified by file metadata, not visually certified. Generated bin/obj products are explicitly excluded from semantic review. Third-party runtime DLLs/localized resources are outside first-party semantic coverage. Neither executable provenance nor the deployed backend/migration revision is established by this audit.

The delivered `generated-artifacts/windows-desktop/ConnectLive-Agent-Windows-x64.zip` contains only a top-level directory with `ConnectLive.exe`, `Start-Agent.cmd`, `README.txt`, and `SHA256SUMS.txt`. Its README calls it an **unsigned portable verification build**, not an installer or production release. It does not include Watch, MSI or Inno. The checked source is not proof that the ZIP executable implements that exact source.

## Confirmed static defects / contract failures

Severity: **High** = core launch/control/update/deployment failure; **Medium** = bounded feature/integrity failure; **Low** = dormant/helper/documentation defect. Reproduction conditions below are derived from actual control/data flow, not observed Windows runs.

1. **High — supplied launcher fails on a fresh profile before enrollment/UI.** ZIP `Start-Agent.cmd:3` passes `--api-url`. `agent/src/App.xaml.cs:51-54` calls `SaveConfig` before constructing `ApiClient` at line 93, and outside the startup try at line 105. `ApiClient.cs:778-781` writes the file without creating its directory; the directory is only created by the constructor at line 126. If `%LOCALAPPDATA%\ConnectLive` does not already exist, `File.WriteAllText` throws. This directly contradicts the documented first-run launcher path. Create/validate the store before saving and catch/report configuration failures.

2. **High — mouse absolute coordinates target the whole desktop, not the monitor being shown.** `ScreenCapture.cs:126-127,230-234` captures `MonitorSelector`'s single monitor. `InputRelay.cs:346-368` maps normalized frame coordinates directly across the *entire virtual desktop*, never using selected-monitor bounds. Two side-by-side equal monitors: a center click on the captured primary maps to the join between monitors, not that monitor's center. Both HTTP and data-channel input reach this same function. Convert normalized coordinates to selected-monitor physical pixels, then normalize against virtual-screen origin/span.

3. **High — installer detection/uninstall metadata uses an UpgradeCode as a ProductCode.** `packaging/msi/ConnectLive.wxs:28-33` declares the fixed GUID as `UpgradeCode`, not `ProductCode`. `packaging/gpo/install-gpo.ps1:12-17` queries `Win32_Product.IdentifyingNumber` for that GUID; `packaging/intune/intune-app.json:7,16-21` also uses it for `/x` and MSI product-code detection. These do not identify the generated product code of the MSI. GPO detection will not match its intended installed product; Intune detection and uninstall instructions are invalid for this package. Use actual product identity or an explicit upgrade-code-aware detection/uninstall strategy. GPO also does not propagate `msiexec`'s exit code (`:27`).

4. **High — standard installed agent cannot perform its in-process self-update.** The manifest is `asInvoker`, `uiAccess=false` (`src/app.manifest:18`); Inno installs in Program Files with `users-readexec` (`ConnectLiveSetup.iss:31,49`) and launches as the original user (`:80`). `SelfUpdate.cs:173-181` attempts to move that protected executable into per-user LocalAppData and copy a replacement back without elevation/helper. This documented standard-user installation path lacks write/delete authority and cannot complete the update. The failed attempt is suppressed for that version for the process lifetime (`:79`). A privileged, explicitly authorized installation/update mechanism is needed; do not grant ordinary users write access to executable install directories.

5. **High — updater has a single-instance handover race that can leave no agent.** `SelfUpdate.cs:196-205` starts the replacement and immediately declares success; `Agent.cs:310-313` then exits. The replacement's `App.xaml.cs:36-41` exits if the existing global mutex is still held, and the original releases it only at exit (`:249-255`). There is no readiness/exit wait, mutex-transfer protocol or rollback when the child exits early. Thus an ordinary scheduling order can make the replacement quit before the parent exits. Portable package has no watchdog to recover. This is a source-proven race, not a measured failure rate.

6. **Medium — remote maintenance/power/monitor commands have no reachable dispatch.** `Agent.cs:296-304` consumes sessions but intentionally no longer calls `DispatchPowerCommands`; the only dispatch implementation at `:345-361` has no caller. Backend `heartbeat.ts:234-259,277` still fetches, marks dispatched and returns commands; `StreamListener.cs:132-136` merely nudges heartbeat. Consequently WoL relay, switch-monitor, restart-stream/agent and power actions in `PowerRelay.cs` are not executed/ACKed by this agent. This fail-closed removal must not be “fixed” by blindly restoring arbitrary power authority: the grant schema has no power capability. Mark unsupported controls explicitly or design an authorized protocol.

   The purported session-input alternative is also unmatched: backend `authorization.server.ts:64-69` and migration `20261021003000_recorded_device_authorization.sql:185-193` classify `restart_stream`, `switch_monitor`, and `clipboard`, but `InputRelay.cs:106-132` implements none. Its poll is control-only (`ApiClient.cs:624-626`) even though backend labels monitor/restart as view capabilities. Clipboard's dedicated WebRTC channel does work statically; this is specifically the HTTP-input protocol mismatch.

7. **Medium — canceled authorization review permanently suspends this running coordinator.** `App.xaml.cs:180` calls `SuspendForAuthorization`, clearing authority/ending the session. If the user closes the review dialog, line 184 returns without `ResumeAfterAuthorization` (only line 188 resumes on a new agreement). `Agent.cs:49-51,72-83` keeps `_authorizationSuspended=true` indefinitely, even though the saved grant remains valid. Cancel should preserve explicit dormant UI state or safely resume only after fresh heartbeat validation; presently it silently leaves an otherwise valid agent unable to accept sessions until review succeeds/restart.

8. **Medium — paused-session contract is incompatible with the authorization migration.** Coordinator expects paused rows and preserved acceptance (`Agent.cs:407-413,434-436,593-611`). Backend heartbeat only retains non-invited rows for which `sessionAuthorized` succeeds (`heartbeat.ts:213-220`); that RPC requires `s.state='active'` (`20261021003000_recorded_device_authorization.sql:98-106`). A paused row is therefore absent and the agent ends it locally (`Agent.cs:442-445`). Migration additionally forbids paused→active (`:150-152`), while agent comments promise resume. Sharing stops safely, but pause/resume is not a supported end-to-end lifecycle under this migration; represent “new invitation required” rather than promise automatic resume.

9. **Medium — file receiver publishes incomplete data as “complete”; advertised SHA verification is absent.** `FileTransfer.cs:154-167` remembers declared size, but `:170-174,201-233` accepts `file_end` without checking `Received == Size` or comparing any expected checksum. It merely computes/logs a local hash. A begin(size=100), one-byte chunk, end writes a one-byte final file and fires `FileLanded`. HTTP fallback similarly stores supplied `x-file-sha256` as metadata without verifying bytes and ignores `x-file-size` (`session.$sessionId.file.ts:70-110`). This is an integrity/false-success defect, not a demonstrated transport attack. Add length/hash protocol validation before atomic publication.

10. **Medium — opt-in H.264 consumes swapped color bytes.** `ScreenCapture.cs:440-467` converts captured BGRA to tightly packed **RGBA** before `PushFrame`, whose contract confirms RGBA (`WebRtcSession.cs:520-523`). That same array is passed unchanged to `PushFrameH264`/`hw.Encode` (`:563-565,631`), while `HwH264Encoder.cs:673-676,690-695` interprets byte 0 as B and byte 2 as R. Red/blue contributions to both luminance and chroma are reversed on H.264. Default is VP8; this finding applies when `CONNECTLIVE_CODEC=auto|h264` and hardware H.264 is negotiated.

11. **Medium — source build's release version is not the executable version.** `build.ps1:56-63,146,169,237-240` generates/publishes an installer/release version, but publish (`:74-81`) does not pass that version to MSBuild; `ConnectLiveAgent.csproj:20` remains `1.9.1`. Agent reports/compares the assembly's three components (`ApiClient.cs:469-474,909-913`). A release advertised with the script's generated `1.0.*.*` can compare *older* than running `1.9.1` and be skipped; an explicitly higher manifest may keep comparing newer after installation because the binary version was unchanged. MSI's generated six-digit third field (`build.ps1:58`) also exceeds Windows Installer ProductVersion's 65535 build-field range; no MSI compilation was run here. Additionally the distribution ZIP from `build.ps1:190-196` contains installers rather than the `ConnectLive.exe` that `SelfUpdate.cs:149-155` requires in a ZIP. Do not publish that installer ZIP as an agent self-update payload.

12. **Medium — headless no-license enrollment cannot reach the claimed “activate later” path.** `ApiClient.cs:199-203` claims headless enrollment is blocked until foreground activation; in reality no meeting ID is sent, enrollment returns unlicensed (`enroll.ts:105-109,199`), and later `EnrollIfNeededAsync` returns immediately when a token exists (`ApiClient.cs:195-197`), so it never asks for a Meeting ID. The recorded-grant RPC requires a license owner (`20261021003000_recorded_device_authorization.sql:86-90`); `authorization.ts:23-27` reports its rejection as 503. Thus a device initially enrolled by `/background` cannot activate via the documented subsequent foreground flow absent an external license binding. Do not restore legacy unlicensed remote access to resolve this: offer an explicit authenticated license-bind/activation path.

13. **Low — Watch's custom-origin config reader disagrees with the writer and transport policy.** Agent `SaveConfig` serializes the PascalCase `AgentConfig.ApiBaseUrl` (`ApiClient.cs:778-781,863`) using default JSON options. Watch expects explicitly lowercase `apiBaseUrl` (`Watch/Program.cs:103-108,152-155`), also using case-sensitive defaults. It falls back to the default endpoint for the agent's saved custom origin. Moreover Watch's own HTTP client has default redirect handling and no `ValidateOrigin` (`:118-126`), unlike main-agent HTTPS/no-redirect policy. **Dormant in reviewed packages:** build scripts/installers/ZIP do not publish Watch. Do not claim an active shipped token disclosure; this is a concrete helper-policy mismatch if Watch is packaged in future.

**Common transport/auth/lifetime:** main `ApiClient` requests use HTTPS origin validation, redirects disabled, 20-second HttpClient timeout and caller cancellation (`ApiClient.cs:124-133`; `NativeGatewayPolicy.cs:11-25`). Device auth is `X-Device-Id` + `X-Device-Token`, checked as SHA-256 against `devices.metadata.token_hash` (`agent-auth.server.ts:8-19`). 401/403 revoke current local live permission and notify teardown; only 401 on non-sensitive paths may enroll a *new device*, then retry once; second 401 imposes 60-second cooldown (`ApiClient.cs:265-324`). Session/ICE/authorization 401 is **never** re-enrolled/replayed. No generalized transient retry or Retry-After handling exists. Handlers have no blanket server deadline; ICE explicitly budgets auth/provider, SSE is long-lived, remaining DB/storage deadlines depend on backend adapters.

## Native permissions, capture and lifecycle notes

- Local grants are bound to canonical HTTPS origin, external device ID and exact server grant record; CurrentUser DPAPI grant persistence differs intentionally from LocalMachine device credentials. Missing/malformed grant, 401/403, heartbeat failure, local disable, pause and end revoke per-peer permission; old permissions cannot be revived (`AuthorizationGrant.cs`, `GrantStore.cs`, `PeerInputPermission.cs`, `Agent.cs`). Device enrollment/presence is not consent. The source-only recorded-authorization migration must be deployed with routes or grants fail closed with 503; no deployed migration status was queried.
- Disable/Close stops local channels before disk/network and saves an explicit withdrawal marker; background/wake launches and Watch honor it. Foreground reauthorization is required to clear it. No deliberate bypass or malware/evasion mechanism was exercised.
- DXGI enumerates adapter/output by selected device name, copies row pitches and rebuilds after access loss/device reset. GDI fallback and a 10s DXGI probe exist. Static limitations: fallback duplication can select default output instead of requested output (`DxgiCapture.cs:93-101`), which is then stale and reinitializes; failed reinitialization leaves a non-null uninitialized DXGI object, while the periodic retry checks only `dxgi==null` (`ScreenCapture.cs:161,193`; `DxgiCapture.cs:435-441`). That path remains on GDI until session restart. Portrait/rotation, multi-GPU, protected desktop, hotplug and secure-desktop behavior require Windows; no performance/color correctness is certified.
- SendInput is non-elevated, so control of higher-integrity/UAC desktops is not supported by the `asInvoker/uiAccess=false` manifest; its return count is ignored (`InputRelay.cs:341`). Do not describe this as elevated system-wide remote control. Held keys/buttons are released by coordinator teardown. `release_inputs` input kind itself only releases curtain (`InputRelay.cs:130-131`), not held keys/buttons.
- InputBlocker uses low-level hooks, 5s curtain ping watchdog, session switch and exit cleanup; hooks accept **any OS-injected input OR magic signature** (`InputBlocker.cs:307-333`), contrary to INSTALL's “both required / third-party injected blocked” statement. Curtain geometry uses WPF DIPs directly from physical Screen bounds (`CurtainOverlay.cs:71-85`), and capture-affinity return is unchecked (`:54`): mixed-DPI coverage/visibility and Ctrl+Alt+Del escape claims are unverified Windows acceptance items.
- VP8 is default, H.264 is opt-in with hardware probe; comments saying the hardware path is unconsumed are stale. Interop vtables/structures and encoder drive were read, not validated against real Windows drivers. No assertion that native COM marshaling, async encoder events, arbitrary-resolution H.264 profile limits or 4K throughput are sound is justified by Linux/static review. H.264 failure logs refer to VP8 fallback, but actual peer remains negotiated H.264 and code does not renegotiate VP8 (`WebRtcSession.cs:601-618`); HTTPS remains the intended safe fallback, not proven live VP8 failover.
- The idle self-update runs inline in the heartbeat loop, not a background worker. Its 10min HttpClient timeout only applies through response headers (`SelfUpdate.cs:123-133`); streaming body has no independent deadline. Presence/invite refresh waits for completion. Hash checking is present; URL-extension-only ZIP detection (`:118`) and lack of signature validation are release constraints, not proof of a malicious published artifact. No release row was published.

## Release decision / remaining runtime gates

**Not release-ready on this review alone.** Resolve the launch blocker, coordinate install/update/version identity, and explicitly reconcile unsupported command/pause/activation contracts before production packaging. Retain fail-closed permission behavior; do not restore broad historical power access or treat old session IDs as consent.

Main reviewer owns baseline/build/test/archive-integrity evidence and any future fixes. Required authorized Windows checks include fresh-profile launcher, non-admin install/update/relaunch, enrollment/license activation, attended/unattended permissions/replacement/cancel, stop offline and restart, selected-monitor input, DXGI/GDI rotation/DPI/hotplug, clipboard/files integrity, actual TURN, takeover, long-lived SSE/network reconnect and end-to-end pause/new-invitation semantics. No Windows hosts are available here, so signed-in/native UI, secure-desktop safety, real capture/input, installer actions and runtime recovery remain **unverified**, not passing.
