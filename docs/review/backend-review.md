# Backend and web-console source review

## Scope and proof limits

Read-only audit of `src`, `supabase`, `scripts`, `tools`, product-root release/configuration files, and relevant workspace verification/packaging source. Only this report and `backend-coverage.json` were written. No product code, database, workflow, release artifact, or environment was changed. No tests, application launch, database checks, route probes, or packaging commands were run; the parent review owns those results.

Findings below are **source-demonstrable**, not assertions about the deployed schema or production exploitability. October defensive migrations are present in source; whether a deployment has them is a separate prerequisite. In particular, an older deployment can have materially weaker direct PostgREST/RPC/storage boundaries. UI behavior was traced in source, not exercised in a signed-in browser. No secret or personal-data values are reproduced.

Coverage is deliberately unequal: a filesystem/text-pattern inventory covered all 245 files under the four principal scoped directories, scanning 1,057,300 characters of text. The route inventory found 45 declarations; all appeared in the generated route tree. This is **not** semantic inspection of every file or proof of route reachability. Coverage entries distinguish targeted reading from automatic inventory, exclusions, and blocked verification. Generated UI primitives, assets, marketing/legal pages, and peripheral integrations are not claimed as fully reviewed.

Severity: **High** = access/payment correctness or a primary shipped workflow fails; **Medium** = important reliability, observability, or resource-control defect; **Low** = misleading secondary state/contract. Paths below are relative to `` unless explicitly prefixed `scripts/`.

## Focused findings

### B01 — High: email-only public lookup discloses private delivery links

- **Evidence:** `src/lib/orders.functions.ts:351–376` exports an unauthenticated POST server function. Its only input is a syntactically valid email. It uses the service-role client to return paid-order IDs, plan, amount, creation time, and `access_link`; there is no email-ownership challenge or authenticated-buyer predicate. `src/routes/license.tsx:74–77` explicitly presents this email-only flow.
- **Impact:** knowing a buyer's email is sufficient to obtain the private provisioning/download link when populated. `src/lib/order-emails.server.ts:89–98` describes that same link as providing installers, Meeting ID and sign-in details and says to keep it private. Exact downstream access depends on the actual delivery page; the source proves link disclosure, not that every link contains reusable credentials.
- **Constraints:** the five-per-email/hour counter limits volume, not ownership. Read/count/insert are separate operations and DB errors are not checked (`orders.functions.ts:359–367`), so this is not a reliable abuse boundary either.
- **Direction:** send an expiring retrieval link to the supplied mailbox, or require verified buyer authentication. Do not return the access link in the initial lookup response.

### B02 — High: webhook matching and state mutation bypass the new unique-quote identity

- **Evidence:** `src/routes/api/public/webhooks/cdp.ts:40–51` resolves an address-only notification with `.maybeSingle()` among pending/detected orders, but `src/lib/cdp.server.ts:28–54` intentionally reuses a wallet address. The quote migration `supabase/migrations/20261021002000_unique_payment_quotes.sql:16–65` disambiguates invoices by coin/address/**amount**, yet the webhook does not use `amount_coin`, coin, or chain to match.
- **Demonstrable failure:** two simultaneously open invoices to the shared address produce a multi-row `.maybeSingle()` error; the error is discarded and the webhook returns success with “no matching order.” ERC-20 polling returns no transactions (`src/lib/cdp.server.ts:100–104`), so this is especially important for the supported stablecoins.
- **Additional state failure:** an explicit `order_id` bypasses even the address filter. `webhooks/cdp.ts:53–77` unconditionally writes the supplied/default status, nullable transaction hash and confirmations without checking invoice amount, chain, confirmation threshold, current terminal state, or transaction uniqueness across invoices. A correctly signed delayed `detected` event can change an already paid/refunded/cancelled order back to detected. The HMAC gate at lines 14–23 is real; this is **not** an unsigned-internet payment-forgery finding. It concerns accepted provider/proxy payloads and replay/out-of-order delivery.
- **Idempotency limits:** `payment_events` uniqueness is `(order_id,tx_hash,event_type)` (`supabase/migrations/20260723184157_a4bb8275-a24a-46d4-a456-26c9d23d2215.sql:99–109`). It neither prevents the same transaction being applied to another invoice nor stops the preceding status update. NULL transaction hashes do not deduplicate under ordinary PostgreSQL UNIQUE semantics. Both writes' errors are ignored and `{ok:true}` is returned.
- **Direction:** one transactional, monotonic payment-acceptance operation shared by webhook and reconciler, exact coin/network/address/amount matching, validated transaction identity and confirmation policy, explicit non-2xx retryable persistence errors.

### B03 — High: web control/reconnect UI still requests transitions the defensive database intentionally rejects

- **Evidence:** web connections always insert an invited **view** session (`src/routes/_authenticated/console.tsx:715–724`). “Curtain (take control)” invokes `toggleControl`, a direct authenticated UPDATE from view to control (`:829–843`, button `:1579–1589`). `supabase/migrations/20261021001000_guard_client_session_transitions.sql:35–38` rejects client control escalation, and `20261021003000_recorded_device_authorization.sql:153–155` separately requires new local session authorization when an active session escalates.
- **Impact:** with these migrations installed, the ordinary web-console start-view → take-control workflow cannot succeed, **even when the recorded device grant includes control**. No new control invitation/local approval path is wired into that action. This is a functional contract break, not a request to weaken consent.
- **Reconnect:** `console.tsx:853–860` writes `state:"active"` directly. This is a harmless touch/downgrade when the row is already active, but it fails for paused sessions, which the table explicitly exposes as reconnectable (`src/components/console/SessionsTable.tsx:80–101`). The database prohibits paused→active (`20261021001000...:25–28`; `20261021003000...:150–152`). Agent reconnect correctly only accepts an already-authorized active session (`src/routes/api/public/agent/session.$sessionId.reconnect.ts:40–62`).
- **Secondary state bug:** `SessionsTable.tsx:102–108` labels a mode toggle “Pause”/“Resume”; it does not change session state. “Pause” on a view session actually attempts to acquire control. Thus labels, state model, and handler disagree independently of deployment.
- **Direction:** explicit capability-aware “request control” through a new invitation/local authorization flow; active-only transport recovery; new invitation for a paused/closed session; distinct pause and release-control semantics.

### B04 — High: standard source build packages an Admin configuration known to fail startup

- **Evidence:** `admin/src/admin.config.json:3–4` has empty Supabase URL and public key. `build.bat:45–51` copies it unchanged into the Admin ZIP; `admin/build.ps1:51–55` does likewise. `admin/src/Api/AppConfig.cs:17–35` gives the executable-adjacent file precedence over the per-user fallback, and `:39–44` rejects empty origin/key.
- **Impact:** publishing with the standard source release entry points does not produce an immediately usable Admin bundle without an explicit configuration step. An invalid bundled file also shadows a valid per-user file. This is not missing-secret disclosure: only deployment URL/public key belong there.
- **Constraint:** the workspace's separate `scripts/package-windows-desktop.py:18–39` explicitly writes a configured public-client file and validates the selected REST project. Therefore this finding **does not assert that the parent's separately packaged desktop ZIP is unconfigured**. Its contents/runtime verification are owned by the parent.
- **Direction:** require validated deployment configuration before source packaging, or intentionally omit an unconfigured adjacent file and clearly support the per-user configuration path.

### B05 — Medium: ordinary admin can bypass super-admin-only manual-payment action through direct table writes

- **Evidence:** `src/lib/orders.functions.ts:189–224` checks super-admin before the manual-paid action and appends payment/audit events. However, `supabase/migrations/20260723184157_a4bb8275-a24a-46d4-a456-26c9d23d2215.sql:77–94` grants authenticated UPDATE and an unrestricted row UPDATE policy to both admin and super_admin. There is no later order-column/state trigger in the inventoried migration source.
- **Impact:** an admin JWT can directly PATCH order status/amount/address/transaction/access fields through PostgREST without the super-admin predicate or mandatory audit path. This contradicts the explicit manual-paid privilege boundary; hiding a button in the separate payments console does not enforce it.
- **Constraint:** the principal is already a payment administrator, not an arbitrary technician or anonymous buyer; actual deployed grants/added policies must be checked independently.
- **Direction:** revoke broad client order mutations, expose narrow audited operations, or enforce protected columns/transitions and actor permissions in SQL.

### B06 — Medium: hello and beacon acknowledge failed writes; stopped beacon always violates notification severity constraint

- **Evidence:** `src/routes/api/public/agent/hello.ts:15–28` awaits but never checks either Supabase update/insert result, then returns `{ok:true}`. Supabase normally reports SQL failures in `error`, not as thrown exceptions. A DB write rejection can therefore leave the device offline and no audit while telling the agent hello succeeded.
- **Concrete schema mismatch:** `src/routes/api/public/agent/beacon.ts:29–43` inserts `severity:"error"` for stopped devices. The notifications constraint only allows info/success/warning/critical (`supabase/migrations/20260722192609_e76e69d7-8f4b-4c64-b780-e0812f5af976.sql:57`). That insert fails on the supplied schema; the failure is ignored and the endpoint returns success (`beacon.ts:48–50`). The uninstalling branch uses warning and does not have this enum mismatch.
- **Other instances:** heartbeat presence/license/status writes (`heartbeat.ts:167–194`) and power ACK writes/audit (`power.$cmdId.ack.ts:30–49`) also do not check SQL errors. These are narrower false-ack risks, not proof that every write currently fails.
- **Direction:** check mandatory write results, return retryable failure, and distinguish partial success; use the actual notification severity enum. Hello success must not imply grant/consent.

### B07 — Medium: SSE is a database poller per connection, silently healthy during database query failures

- **Evidence:** `src/routes/api/public/agent/stream.ts:55–83` performs one power-command SELECT per connected stream each second. No per-device connection cap/shared subscriber exists. The query destructures only `data` (`:57`); Supabase `error` is ignored, so normal SQL/network error results do not reach the exception handler. Ready/keepalive still flow. Native `agent/src/StreamListener.cs:109–136` marks the channel healthy after headers, ignores error events, and has no idle/read watchdog.
- **Impact:** at N idle devices this adds roughly N reads/sec (plus heartbeats), before multiple connections/replicas; 1,000 streams imply roughly 86.4 million command SELECTs/day if uninterrupted. This is an arithmetic load projection, **not a benchmark or observed capacity result**. A failed poll can leave the client on its slow heartbeat cadence, so fast wake delivery is lost without an obvious health transition.
- **Boundary:** only queued `wake_agent` commands are accelerated; ordinary session invitations and other power kinds are heartbeat-delivered. The native idle loop chooses 60 seconds with a healthy SSE stream (`agent/src/Agent.cs:286–320`). The web presence model marks reconnecting after 30 seconds (`src/lib/console-types.ts:38`), so a normally idle SSE-connected device can repeatedly appear reconnecting between successful minute-spaced heartbeats. Server reaper uses three minutes (`supabase/migrations/20260803085521_a702e455-40f5-4dd6-a3d6-65b32dd41f66.sql:62–68`), not the web threshold.
- **Direction:** shared event dispatch or batched polling with connection admission, explicit DB-error health, bounded reconnect/watchdog semantics, and presence thresholds matched to actual idle cadence.

### B08 — Medium: payment reconciler has unbounded provider waits, lossy history/error handling and a separate completion path

- **Evidence:** `src/lib/cdp.server.ts:74–104` has no fetch deadline, scans only the newest 25 BTC transactions, and returns `[]` for API errors or unsupported stablecoin polling. `src/routes/api/public/cron/reconcile-orders.ts:63–86` processes up to 200 invoices sequentially and treats this empty result as “no payment,” allowing pending invoices to expire after the grace minute even on provider failure. Expired invoices are no longer queried. Recent-history eviction can also miss an otherwise valid payment at a busy reused address.
- **Completion difference:** `reconcile-orders.ts:93–120` changes status and appends an event but never dispatches the confirmed email. The webhook (`webhooks/cdp.ts:79–85`) and manual-paid action do dispatch it. This is a real lost customer-notification branch, not proof that license provisioning was supposed to be automatic; the template explicitly promises later manual delivery.
- **Constraint:** source's exact-amount comparator and permanent quote reservation materially improve matching; they do not solve provider availability/history depth or transaction/status atomicity. Existing pre-migration overlapping quotes require separate remediation.
- **Deployment concern:** `supabase/migrations/20260803090421_b8368cb5-f1ed-4a68-b4a3-56fdd4c75a17.sql:16–24` embeds the old hosted-app cron destination, not runtime configuration. A new deployment must deliberately replace the scheduled destination. The workspace fresh-install path may adapt historical SQL; this report does not claim the live cron still uses that URL.

### B09 — Medium: chunk-upload fallback admits unbounded unpublished bytes before enforcing session quota

- **Evidence:** `src/routes/api/public/agent/session.$sessionId.file.ts:55–68` reads the entire request, checks 8 MiB **after** allocation, and stores each part without a cumulative-parts quota or reserved transfer size. Only EOF (`:70–99`) assembles all listed parts and checks the 500 MiB/file and 5 GiB/session manifest limits. `x-file-size` is documented but unused.
- **Impact:** an authorized files-capable endpoint can create arbitrarily many part/fileId objects without EOF, bypassing the manifest-based session quota; assembly can download thousands of parts before discovering an oversized file. In the inspected migration source, session cleanup removes manifests/ephemera, not these stored objects. Storage lifecycle policies outside this source could mitigate accumulation.
- **Constraint:** this requires an enrolled device with an active files grant/session; it is not unauthenticated bucket access. The latest restrictive storage policy deliberately blocks direct client access.
- **Direction:** bounded streaming intake, per-transfer/session byte reservation, integer sequence and completeness checks, failed-transfer cleanup/TTL, and size/hash validation before publication.

### B10 — Low: audit subscription is not published in source; five-second polling is the actual fallback

- **Evidence:** `src/routes/_authenticated/console.tsx:167–174` subscribes to `audit_logs` and always refreshes every five seconds. Migration text publishes devices, sessions, frames, signals, cursors, notifications and power_commands, but contains no audit_logs publication addition. `refresh():581–598` makes four SELECTs every time, with no error UI, cancellation or overlap/coalescing guard.
- **Impact:** an audit-only event need not push immediately on a deployment following this source publication set. It is **not missing audit UI**: the timer retrieves the newest 50 visible rows, and the audit tab renders them (`:1383–1408`). Expected latency is polling-bound and refresh errors can leave stale state looking current. Fleet/session events also cause whole-dashboard refreshes in addition to the timer.
- **Constraint:** a live publication can differ from migration source. Do not report this as an observed production realtime outage.

### B11 — High, deployment-conditional: workspace deployment excludes the active ConnectLive runtime

- **Evidence:** workspace `.replitignore:9–10` excludes the entire `imports` directory as “inactive imported source.” However, `artifacts/connectlive-preview/package.json:7–9` now delegates dev/build to the imported product and its serve command explicitly runs `../../.output/server/index.mjs`.
- **Impact:** a deployment that honors this exclusion cannot use that artifact's declared serve entry, because the active server output is under the excluded directory. A successful local preview or product build does not establish deployment packaging completeness.
- **Constraints:** deployment execution was not attempted. A deployment process that explicitly stages the server output elsewhere could avoid this issue, but no such staging exists in the inspected artifact scripts. This is separate from the product's standalone Docker build, which copies its own `.output`.
- **Direction:** explicitly package the active runtime outside excluded reference imports, or narrowly adjust deployment exclusions after verifying no archives, credentials or native build outputs are included.

## Authority, lifecycle, and storage trace

1. **Login is not role authorization.** `src/routes/api/public/auth/login.ts` validates password via Supabase and returns access/refresh tokens. Its account lockout table is application-local; direct Supabase password sign-in remains a separate surface, and concurrent read/increment/write is not atomic. `requireSupabaseAuth` checks signed JWT claims and constructs a JWT-scoped client. `src/start.ts:21–24` registers the browser bearer-attacher globally; no missing global auth middleware was found.
2. **Role boundaries are mixed but intentional in several places.** The pathless authenticated layout checks that a user exists, not staff status. `/payments` separately gates its panel to admin/super_admin; the underlying orders reads generally rely on RLS. `getPaymentsHealth` is auth-only and uses service role (`orders.functions.ts:323–345`), exposing setup booleans to any signed-in user, a lesser disclosure than B01. `/console` can render for other roles but server/RLS remains the real boundary. Do not equate a visible console shell with successful remote access. Team operations check super_admin in server functions. Role replacement (`admins.functions.ts:95–106`) deletes then inserts without a transaction or delete-error check; a failed replacement can leave no role.
3. **Enrollment is not consent.** Keyless enrollment mints a random token and stores SHA-256 only; subsequent device requests verify both external device ID and token hash. The enrollment throttle is best-effort DB read/upsert based on forwarded IP, not a hard distributed quota. Wrong Android claim codes do not fail enrollment; they leave pairing unclaimed, as documented. Meeting-ID binding is separate from local access approval. Fresh unlicensed or ownerless devices cannot record an effective grant under the latest SQL because `record_device_authorization` requires a license owner.
4. **Recorded authority is materially stronger than legacy timestamps.** Strict grant-shape/capability parsing, service-role-only grant RPCs, one-current-grant uniqueness, revocation ending live sessions/deleting channels, owner binding, explicit active-session checks and no legacy fallback are present. `session_authorized` and restrictive channel policies do not trust `devices.is_session_active`. Native consent includes authorization ID and notice version; the agent HTTP accept handler requires them and uses a guarded invited-state UPDATE. Reconnect is transport recovery, not activation. These are source controls, contingent on applying the complete migration.
5. **Direct APIs must be evaluated separately from wrappers.** Latest SQL restricts `bind_admin` to authenticated session owner/super_admin, validates client ID and revokes service_role execution; web wrapper uses JWT client. Session transition and recorded-authority triggers also guard direct table writes. Older permissive owner/staff channel policies remain in history but are ANDed with the latest restrictive policies; it would be incorrect to report those historical policies alone as a current arbitrary-frame-read bypass. The ordinary-admin order bypass B05 remains outside that hardening.
6. **Files:** web server functions and native stable HTTP routes check owner/super_admin plus active files authority. Private bucket direct authenticated access is denied by `recorded_storage`; identifier-only byte URLs require fresh JWT authentication, and byte handlers recheck authority around reads/building ZIPs. No bearer download URL issuance was found in the inspected new proxy path. SQL serializes manifest quota admission against session changes. In contrast, B09 concerns unpublished agent chunk objects, not the guarded manifest path. Object transfer already delivered over a datachannel or HTTP response cannot be retroactively revoked; authority is checked before publication/dispatch, not by erasing bytes from a recipient.
7. **ICE:** both peers require a session ID, active owner/device relationship and view grant. Technician role checking is explicit; mint budget is process-local (edge limits needed across replicas). Auth phase races a four-second budget; Cloudflare endpoints share a five-second provider/body deadline; client callers use approximately 12-second budgets. Cloudflare → coturn REST → static credentials → explicit STUN-only fallback is present, and response is no-store. An auth budget timeout does not cancel outstanding Supabase work. TURN credentials have 12-hour TTL; later consent revocation cannot revoke already minted TURN credentials, although session application channels still require authority. No claim of tested relay connectivity or production credentials is made.

## Release and runtime boundaries

- **Docker source is plausible, not runtime-verified:** `Dockerfile:4–35` builds with frozen Bun lock and explicit `NITRO_PRESET=node-server`, requires public Vite URL/key at build time, then copies only `.output` into Node 24 Alpine. - Runtime credentials remain required for Supabase/service role, session-secret wrapping, SMTP/cron/TURN as used. Docker does not create them and liveness does not verify them. The private session-files bucket is also an external readiness dependency, not established by this liveness check. Browser Vite config is baked at build time; changing only server runtime Supabase values can split browser/server projects. `.dockerignore` excludes environment files, native/build directories, archives and signing material. No image build, native-module ABI, writable-temp, outbound-network or health-restart behavior was executed here.
- `vite.config.ts` delegates plugin/preset handling to the Lovable config package and points to the custom server entry; its comments are not independent proof of the emitted runtime. Root workspace typecheck only explicitly filters artifacts/scripts, not imported-product source; a green workspace typecheck is not an imported product semantic-typecheck result. Root recursive build can still run the product build.
- `build.bat` packages standalone Agent/Admin executables, whereas `agent/build.ps1` builds installer variants and optional Watch/packaging flows. Treat them as different release products, not interchangeable proof of installation/persistence. Standard sign helper warns and returns success without signing credentials, and verifies signatures when configured. Production signed-release policy must not rely on build success alone. Authenticode execution was not possible on this host and was not attempted.
